SLIDE 2: INTRODUCTION & OBJECTIVES
================================================================================
[Visual / Layout Suggestion]:
  - Two-column split: Left side shows "The Campus Challenge", Right side shows "Core Objectives" with checkmark icons.

SLIDE CONTENT:
  • BACKGROUND & PROBLEM STATEMENT:
      - University fests, hackathons, and symposiums involve thousands of participants.
      - Fragmented announcements across WhatsApp, unofficial chats, and bulletin boards.
      - Gate check-ins rely on chaotic paper lists, creating long queues and proxy entries.
      - Organizers suffer severe budget waste from unpredictable student turnout.
  • CORE OBJECTIVES:
      - Unified Discovery: Centralized, filterable catalog for all campus activities.
      - Fraud-Proof Ticketing: Automated issuance of single-use, cryptographically verified QR passes.
      - Zero-Install Gate Scanner: In-browser camera QR scanner (html5-qrcode) for instant check-in.
      - AI Turnout Forecasting: Scikit-Learn regression model to predict actual attendance.
      - Integrated Commerce & Governance: Secure Razorpay payment pipeline and host volunteer whitelisting.

SPEAKER NOTES (Time: 0:45 - 2:00):
  "In any college environment like ours, organizing events involves huge logistical
  overhead. Announcements are scattered across unofficial WhatsApp groups, paper forms
  lead to data loss, and physical gate check-ins allow proxy attendance. Most importantly,
  organizers never know how many students will actually turn up, leading to wasted
  catering budgets or overcrowded auditoriums.
  Our objective with CampusIQ is to provide a single unified ecosystem: students can
  discover events and book digital passes; student volunteers scan tickets in real
  time using their smartphone web cameras; and organizers gain AI-driven turnout
  predictions to plan seating and catering scientifically."

  First, Google Forms with WhatsApp: widely used, but lacks ticketing, security, or
  instant verification. Second, commercial platforms like Eventbrite: they are built
  for commercial profits, charge per-ticket fees, and cannot capture college-specific

  paper passes, which are prone to proxy entries and forgery. This literature survey
  demonstrated a clear need for a dedicated, institutional event management platform."

SLIDE 4: CURRENT SOLUTIONS ANALYSIS & WHY CAMPUSIQ IS NEEDED
================================================================================
[Visual / Layout Suggestion]:
  - Three visual callout cards: 1. Turnout Crisis, 2. The Proxy Loophole, 3. The CampusIQ Advantage.

SLIDE CONTENT:
  • THE TURNOUT UNCERTAINTY CRISIS:
      - For free college events, 30% to 50% of registered students fail to show up.
      - Organizers over-order catering and over-book auditoriums, causing severe budget waste.
      - CampusIQ solves this by feeding event fee, venue limit, and registrations into an ML model.
  • GATE BOTTLENECKS & TICKET FRAUD:
      - Manual paper cross-referencing takes 30–45 seconds per attendee.
      - Screenshots of free passes are shared with unregistered friends.
      - CampusIQ checks in attendees in under 1.5 seconds and invalidates used passes atomically.
  • KEY DIFFERENTIATORS OF CAMPUSIQ:
      - Academic-Aware RBAC: Captures college, course, department, semester, and roll number.
      - Zero-Install Web Camera Scanner: Volunteers require no app downloads—it runs in the browser.
      - Cryptographic Security: Single-use 128-bit UUID tokens stored as TICKET:<token>.
      - Integrated Host Volunteer Management: Hosts review and whitelist volunteer applications.

SPEAKER NOTES (Time: 3:15 - 4:15):
  "Why is a new solution necessary? Primarily because of two major pain points:
  First, the 'no-show' phenomenon. When registration is free, students register
  casually and don't show up, leaving organizers with empty seats and wasted food.
  CampusIQ uses a machine learning model to estimate true turnout before the event begins.
  Second, security at the gates. With manual lists, volunteers spend 45 seconds per
  student, and students easily share pass screenshots. CampusIQ reduces check-in to
  1.5 seconds via web camera scanning, and marks the pass as used instantly in the
  database, completely blocking proxy attendance."

SLIDE 5: REQUIREMENTS ANALYSIS (HARDWARE & SOFTWARE TOOLS)
================================================================================
[Visual / Layout Suggestion]:
  - Two distinct panels: Left side for Software Stack, Right side for Hardware & Infrastructure.

SLIDE CONTENT:
  • SOFTWARE TOOLS & STACK:
      - Client Layer: React 19 (Vite bundler), TailwindCSS, Lucide-React, React Router DOM v7
      - Scanner Engine: html5-qrcode (hardware-accelerated in-browser video barcode decoder)
      - Application Server: FastAPI (Python 3.10+) running on Uvicorn ASGI server
      - Database & ORM: PostgreSQL (Production) / SQLite (Development), SQLAlchemy 2.0 ORM
      - Security & Cryptography: Passlib (Bcrypt hashing), Python-JOSE (HS256 JWT tokens)
      - Machine Learning: Scikit-Learn (Linear Regression), Pandas, Joblib serialization
      - Cloud Integrations: Razorpay SDK (Payments), Cloudinary API (Poster & QR CDN)
  • HARDWARE & ENVIRONMENT REQUIREMENTS:
      - Development Server: 64-bit multi-core CPU (Intel/AMD), 8 GB RAM, 20 GB storage
      - Host & Student Devices: Any standard laptop, PC, tablet, or smartphone (Chrome, Safari, Edge)
      - Volunteer Scanner Devices: Any basic smartphone with a functional camera & browser
      - Production Cloud Infrastructure: Render PaaS (Linux container) + Managed PostgreSQL

SPEAKER NOTES (Time: 4:15 - 5:15):
  "Moving to our requirements analysis: On the software side, we selected FastAPI for
  our backend due to its asynchronous performance, automatic OpenAPI documentation,
  and native integration with Python's data science ecosystem. We use SQLAlchemy ORM
  with PostgreSQL. On the frontend, React 19 bundled with Vite and styled with
  TailwindCSS provides a responsive UI. We utilize html5-qrcode for browser-based
  camera scanning, Scikit-Learn for turnout prediction, and Razorpay for payment
  processing.
  On the hardware side, the architecture is lightweight. No specialized barcode
  hardware is needed; any standard smartphone carried by student volunteers acts as
  a high-speed ticket scanner."

SLIDE 6: SYSTEM DESIGN & ARCHITECTURE
================================================================================
[Visual / Layout Suggestion]:
  - 3-tier architectural diagram showing Frontend, Backend API, Database, ML Engine, and Cloud APIs.

SLIDE CONTENT:
  • 3-TIER DECOUPLED ARCHITECTURE:
    ┌────────────────────────────────────────────────────────┐
    │                   REACT 19 FRONTEND                    │
    │   [Student Portal]   [Host Dashboard]   [QR Scanner]   │
    └──────────────────────────┬─────────────────────────────┘
                               │ REST API (JSON / Bearer JWT)
    ┌──────────────────────────▼─────────────────────────────┐
    │                   FASTAPI BACKEND                      │
    │  [Auth & RBAC]  [Event Engine]  [Anti-Fraud Scanner]   │
    │  [Razorpay Verification]        [AI Prediction Engine] │
    └────────────┬──────────────────┬─────────────────┬──────┘
                 │                  │                 │
        ┌────────▼───────┐  ┌───────▼───────┐  ┌──────▼──────┐
        │  PostgreSQL /  │  │  Cloudinary   │  │ Scikit-Learn│
        │  SQLAlchemy    │  │  Media CDN    │  │ Linear Reg. │
        └────────────────┘  └───────────────┘  └─────────────┘

  • CORE OPERATIONAL WORKFLOWS:
      1. Booking Workflow: Student registers -> Razorpay verification (if paid) -> Unique UUID generated -> QR code rendered & saved to Cloudinary.
      2. Gate Check-in: Volunteer scans pass -> Backend checks ticket validity and checked_in == False -> Marks checked_in = True -> Re-scans trigger immediate fraud alert.
      3. AI Analytics: Host views analytics -> Feature vector [limit, fee, registrations] fed into model -> Predicted attendance displayed.

SPEAKER NOTES (Time: 5:15 - 6:45):
  "This diagram illustrates our end-to-end system design. The client layer is a React SPA
  communicating via REST and Bearer JWTs with our FastAPI server.
  The workflow operates in three stages:
  First, the Booking Workflow: When a student books a ticket, the system validates event
  capacity, handles Razorpay payment verification if the event is paid, and mints a
  single-use QR pass with a unique UUID.
  Second, the Gate Check-in Workflow: At the event hall, whitelisted volunteers open the
  in-browser scanner. The backend performs an atomic check. If valid, the ticket is
  marked as checked in. If someone attempts to re-use the same ticket screenshot,
  the system instantly flashes a red fraud warning.
  Third, the Prediction Workflow: Our trained Linear Regression model evaluates registration
  velocity, ticket fee, and participant limit to output forecasted attendance for the host."
